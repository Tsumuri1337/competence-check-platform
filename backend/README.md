# Competence-check platform — backend

Проверка компетенций на основе действующих профессиональных стандартов
Минтруда России в области информационной безопасности. Кандидат или
сотрудник проходит по выбранному профстандарту самооценку (по желанию),
тест знаний и практическое задание; ревьюер оценивает практическое
задание и видит сводный (для кандидатов — также комплексный) отчёт.

## Профстандарты

Пять действующих профстандартов (группа 06 «Связь, информационные и
коммуникационные технологии», реестр Минтруда):

| Код | Название | Приказ |
|---|---|---|
| 06.030 | Специалист по защите информации в телекоммуникационных системах и сетях | №536н, 14.09.2022 |
| 06.032 | Специалист по безопасности компьютерных систем и сетей | №533н, 14.09.2022 |
| 06.033 | Специалист по защите информации в автоматизированных системах | №525н, 14.09.2022 |
| 06.034 | Специалист по технической защите информации | №474н, 09.08.2022 |
| 06.053 | Специалист по информационной безопасности в кредитно-финансовой сфере | №739н, 28.11.2022 |

Полная структура каждого стандарта (обобщённые трудовые функции → трудовые
функции → знания/умения) транскрибирована из официальных PDF и хранится в
`src/content/*.json` (источник для `seed.js`). Транскрипция сделана
построчным визуальным чтением отрендеренных страниц PDF (не через
автоматическую суммаризацию — см. `HANDOFF.md`), поэтому это реальный,
проверяемый по первоисточнику текст:

| Код | ОТФ | ТФ | Знаний+умений | Вопросов в банке | Заданий в банке |
|---|---|---|---|---|---|
| 06.030 | 7 | 20 | 215 | 213 | 20 |
| 06.032 | 5 | 20 | 387 | 382 | 20 |
| 06.033 | 4 | 21 | 294 | 291 | 21 |
| 06.034 | 12 | 38 | 588 | 591 | 38 |
| 06.053 | 6 | 25 | 380 | 409 | 25 |

Тест знаний и практическое задание — авторский контент, составленный на
основе этих знаний/умений, а не цитаты из стандарта. Самооценка охватывает
100% транскрибированных пунктов каждого стандарта. Банк вопросов покрывает
темы по всем трудовым функциям (примерно по вопросу на пункт знаний/умений),
а практических заданий — не менее одного на каждую трудовую функцию (ТФ),
не только на обобщённую (ОТФ).

Вопросы — предметные (определение, назначение, отличие понятий, принцип,
короткая ситуация), а не «что включает трудовая функция»: такие мета-вопросы
проверяют сопоставление формулировок стандарта, а не знание, и были убраны.
Проверяется скриптом при слиянии: в тексте нет отсылок к ТФ/кодам, у каждого
вопроса 4 разных варианта одной длины (максимум/минимум ≤ 1.4), верный ответ
самый длинный примерно в 28% случаев (при равной вероятности 25%), дублей
формулировок нет. **Фактическую точность банка проверял только автор-
генерация без внешних источников — перед боевым использованием нужна
экспертная вычитка ИБ-специалистом**, особенно вопросов про нормативные
органы и стандарты (ФСТЭК, ФСБ, Банк России, ГОСТ, ISO).

### Случайная выборка при прохождении

Из этого банка каждая конкретная проверка получает случайную выборку —
**50 вопросов теста знаний** и **2 практических задания** — в случайном
порядке, с перемешанными вариантами ответа у каждого вопроса. Выборка
делается один раз при первом обращении к `/quiz` или `/practical-task` и
сохраняется в `assessments.quiz_assignment` / `task_assignment` (JSONB), а
не пересчитывается заново — поэтому обновление страницы или восстановление
прогресса (см. ниже) показывает тот же набор в том же порядке, а не новую
выборку. Ответ, отправленный клиентом с индексом перемешанного варианта,
на сервере переводится обратно в исходный индекс перед сверкой с
`correct_index` и сохранением в `quiz_responses` — сравнение и отчёты
ревьюера работают с исходными индексами, о перемешивании не знают.
Завершение проверки по практическому заданию тоже считается по выборке
конкретной проверки (2 задания), а не по всему банку заданий стандарта.

## Стек

Express (`src/server.js`) + Postgres через `pg` (`src/db.js`, тот же
`transaction()`-паттерн, что и раньше). Соединение читается из
`DATABASE_URL` (см. `.env.example`); по умолчанию — локальный dev-адрес
`postgresql://hr_poc_app:hr_poc_app_dev@localhost:5432/hr_poc`.

## Запуск

Нужен запущенный Postgres (локально или через `DATABASE_URL`).

```bash
npm install            # Express, pg, cors
npm run migrate        # применяет src/schema.sql
node src/seed.js       # загружает 5 профстандартов + демо-контент
node src/server.js     # http://localhost:3001
```

Все страницы раздаются backend'ом напрямую из корня проекта, API — на том же
origin (нужно для сессионных кук): `http://localhost:3001/` — главная (выбор
входа), `test_flow.html` — личный кабинет кандидата/сотрудника и прохождение
проверки, `reviewer_dashboard.html` — панель ревьюера, `requirements.html` —
справочник требований.

Для OSINT-поиска профилей нужен Sherlock (необязательно — без него
проверяется только Credly, и это видно в отчёте):

```bash
pipx install sherlock-project     # или: pip install sherlock-project
export SHERLOCK_BIN=sherlock      # путь к бинарнику, если он не в PATH
```

AI-резюме кандидата можно получить без ключа API — через свой чат-ассистент
(Gemini, Claude и т.п., см. «Ручной режим» ниже). Для автоматического режима
одной кнопкой нужен ключ Claude API (без него кнопка сообщает, что AI не
настроен, остальное работает):

```bash
export ANTHROPIC_API_KEY=sk-ant-...
```

Если сервер ходит в интернет через прокси, Node 22 сам его не подхватывает —
запускайте с `NODE_USE_ENV_PROXY=1` (Credly-запросы идут через встроенный `fetch`).

## Тесты

```bash
npm test    # node --test, без дополнительных зависимостей
```

Тесты (`test/*.test.js`) — интеграционные: поднимают Express-приложение на
случайном порту и обращаются к нему обычным `fetch`, как реальный клиент.
Покрывают случайную выборку теста/заданий и её стабильность между
запросами, перевод перемешанного индекса ответа обратно в исходный при
подсчёте баллов, завершение проверки по выданным (а не по всем) заданиям,
вход/выход ревьюера и защиту эндпоинтов сессией, а также запрет решения по
кандидату для `context=employee`.

Каждый тест создаёт только свои строки (уникальный email) и удаляет их в
`after()` — набор безопасно гонять как на локальной dev-БД (общий контент
профстандартов не трогается), так и на чистой БД в CI. CI (`.github/workflows/ci.yml`)
поднимает Postgres как сервис-контейнер, применяет `migrate`+`seed` и
гоняет тот же `npm test` при каждом push/PR в `main`.

## Данные и роли

- **Кандидат/сотрудник** — регистрируется в личном кабинете (ФИО, email,
  телефон, пароль, контекст `employee`/`candidate`, необязательный никнейм для
  OSINT, обязательное согласие на проверку профилей и сертификатов), дальше
  входит по email/паролю. Та же модель сессии, что у ревьюера, но отдельная
  кука (`person_session`) и таблица `person_sessions`; та же защита от
  перебора (ключ `person-email:…`). Проверки привязаны к человеку из сессии:
  все эндпоинты `/api/assessments/:id/*` для прохождения отвечают 404 на
  чужую проверку — раньше достаточно было знать id. Телефон и никнейм хранятся
  зашифрованными, как ФИО и email.
  Демо-кандидат после `seed.js`: `candidate@example.ru` / `candidate123`.
- **Ревьюер** — реальный вход по email/паролю (`POST /api/auth/login`).
  Пароль хранится как scrypt-хэш (`src/lib/auth.js`, встроенный `crypto`,
  без новых зависимостей), сессия — httpOnly-кука со случайным токеном;
  на сервере хранится только sha256 токена (`reviewer_sessions`), сам
  токен нигде не сохраняется. Раньше это была открытая заглушка через
  заголовок `X-Reviewer-Email` — теперь `reviewer_id` берётся только из
  проверенной сессии, его нельзя подделать заголовком.
  Демо-ревьюер после `seed.js`: `reviewer@example.ru` / `reviewer123`.
  Новых ревьюеров создаёт администратор через CLI (саморегистрации нет —
  сознательно, это инструмент только для нанятых ревьюеров); тот же
  скрипт сбрасывает забытый пароль, отзывает старые сессии и снимает
  блокировку входа:
  ```bash
  node src/create-reviewer.js "Имя Фамилия" email@example.ru пароль
  ```
  Пароль — от 10 символов. **Защита от перебора:** 5 неудачных попыток за
  15 минут блокируют вход по этому email (ответ 429 с `Retry-After`), 30 — с
  одного IP; счётчик хранится в БД (`login_attempts`), переживает перезапуск и
  считается и для несуществующих email, чтобы блокировка не выдавала, какие
  адреса зарегистрированы. Для неизвестного email всё равно считается
  scrypt, чтобы по времени ответа нельзя было отличить его от неверного
  пароля. Вошедший ревьюер меняет пароль сам (`POST /api/auth/change-password`,
  ссылка «Сменить пароль» в панели) — остальные его сессии при этом
  отзываются.

## Что реализовано

- Пять профстандартов с полной структурой ОТФ/ТФ/знания/умения.
- Три этапа проверки, в порядке прохождения: самооценка (по желанию,
  всегда предлагается и всегда пропускаема — см. ниже), тест знаний
  (авто-оценка), практическое задание (оценка ревьюером по рубрике,
  завершает проверку). Самооценка идёт первой, а не последней, чтобы
  собственная оценка навыков не была искажена уже увиденным результатом
  теста.
- Тест знаний и практическое задание — случайная выборка из полного банка
  для каждой проверки (50 вопросов / 2 задания), в случайном порядке, с
  перемешанными вариантами ответа — см. «Случайная выборка при
  прохождении» выше.
- Валидация анкеты и ответов на клиенте: формат email, обязательные поля,
  непройденные вопросы/задания/пункты самооценки подсвечиваются и
  прокручиваются в поле зрения перед отправкой.
- Сводный отчёт для ревьюера: результат теста, статус практического
  задания, самооценка по каждому пункту.
- **Комплексный отчёт** для обоих контекстов: сводка «% по тесту / средний
  балл по практическому заданию / пройдена ли самооценка». Для кандидатов
  (`context=candidate`) под сводкой добавляется решение по найму —
  `accepted` / `rejected` / `pending`, сохраняется через
  `POST /api/assessments/:id/decision` и видно в списке проверок ревьюера.
  Для сотрудников это только сводка, без каких-либо кнопок решения — оценка
  их дальнейшей судьбы вне объёма этого среза.
- **«Скачать PDF»** в комплексном отчёте — не отдельная генерация PDF, а
  печать браузера (`window.print()`) с выделенным print-стилем: список,
  фильтры, полный текст заданий/рубрик и построчная самооценка скрываются,
  остаётся сжатая сводка на 1-2 страницы (имя, стандарт, баллы, решение).
  Пункт «Сохранить как PDF» есть в диалоге печати любого современного
  браузера — отдельная зависимость не нужна.
- Журнал доступа — каждый просмотр отчёта, оценка задания и решение по
  кандидату записываются в `access_log`.
- Восстановление прогресса после обновления страницы (`test_flow.html`):
  ID проверки, текущий шаг и ответы теста знаний (какой вопрос, какие
  варианты уже выбраны) сохраняются в `localStorage`; при повторном
  открытии страницы, если проверка ещё не завершена, предлагается
  продолжить с того же места или начать заново. Кнопка «Начать заново»
  доступна на каждом шаге (кроме анкеты) и очищает сохранённый прогресс.
- Шифрование ПДн на уровне приложения: ФИО и email кандидатов/сотрудников
  хранятся в БД как AES-256-GCM (`src/lib/pii.js`, встроенный `crypto`), так что
  дамп или бэкап базы сам по себе их не раскрывает. Ключ — переменная
  `PII_ENCRYPTION_KEY` (32 байта, hex из 64 символов или base64); в production
  без неё сервер не стартует, вне production берётся небезопасный dev-ключ с
  предупреждением. Поиск и уникальность по email — через детерминированный
  HMAC-хэш (`people.email_hash`, blind index), потому что шифртекст со случайным
  IV для этого не годится. `npm run migrate` шифрует уже существующие
  открытые записи. Открытый эндпоинт `GET /api/assessments/:id` больше не
  отдаёт ФИО/email — их видит только авторизованный ревьюер.
  Сгенерировать ключ: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
- Реальная аутентификация ревьюера — вход по email/паролю с сессией на
  httpOnly-куке (см. «Данные и роли» выше). Кандидат/сотрудник по-прежнему
  не авторизуется — это осознанное решение (они не заводят аккаунт, а
  проходят разовую проверку по ссылке).

## OSINT: проверка сертификатов и профилей

Запускается в фоне при регистрации (и при смене никнейма; повторно — кнопкой
кандидата не чаще раза в 5 минут или кнопкой ревьюера). Код — `src/lib/osint/`,
результат — таблицы `osint_runs` и `certificates`.

1. **Sherlock** (`osint/sherlock.js`) — внешний CLI, ищет аккаунты по никнейму
   (указанный кандидатом + начало email) на ИБ-значимых сайтах: GitHub, GitLab,
   Hack The Box, TryHackMe, HackerOne, Bugcrowd, PentesterLab, CryptoHack,
   Credly, AWS Skills Profile, Habr и др. (`SECURITY_SITES`). Это «возможные»
   профили: Sherlock проверяет только существование аккаунта с таким ником.
   Сайты с частыми ложными срабатываниями (Reddit) исключены.
2. **Credly** (`osint/credly.js`) — публичные бейджи профиля
   (`/users/<slug>/badges.json`) по никнеймам и по адресу из ФИО
   (`ivan-petrov`). Каждый бейдж проверяется через Open Badges assertion:
   в нём хэш email получателя, поэтому принадлежность бейджа кандидату
   проверяется без доступа к его email на Credly.
   - email совпал → `verified`;
   - профиль указан кандидатом, совпало только имя (кириллица/латиница,
     разные транслитерации — `osint/names.js`) → `probable`;
   - профиль указан кандидатом, не совпало ничего → `owner_mismatch`;
   - профиль **угадан по ФИО** — засчитываются только бейджи с совпавшим
     email, остальное не сохраняется (иначе в отчёт попадают сертификаты
     однофамильцев — на реальном Credly это проверено: у «ivan-petrov» есть
     чужие бейджи).
   Бейдж распознаётся как сертификат из каталога по названию и издателю;
   учебные бейджи («Training Badge», «Introduction to …») не засчитываются.
3. **Заявленные кандидатом сертификаты** — ссылка на бейдж Credly проверяется
   тем же assertion; для вендоров без открытого API (Huawei, Microsoft,
   EC-Council, Hack The Box) — статус `needs_manual` и ссылка на страницу
   проверки вендора с номером сертификата. Заявленный сертификат, найденный
   подтверждённым бейджем Credly, подтверждается автоматически.
4. **Ревьюер** подтверждает или отклоняет любой сертификат вручную; повторный
   OSINT это решение не перетирает. Бейджи, которые повторный поиск больше не
   находит, удаляются (кроме решённых ревьюером).

Телефон в OSINT не используется (открытых источников сертификатов по
телефону нет) — он хранится для связи с кандидатом.

Каталог сертификатов — `src/content/certifications.json`: Cisco, Huawei,
CompTIA, ISC2, AWS, Microsoft, Google Cloud, OffSec, EC-Council, Hack The Box;
у каждого — темы требований, которые он подкрепляет, и способ проверки.
Страница проверки Huawei с сервера разработки не открылась (403, защита от
ботов), её адрес стоит перепроверить в браузере.

## Справочник требований и тематический индекс

Иерархия (вкладка «Требования», `requirements.html`):

- **Должность** — профстандарт (06.030 …).
- **Компетенция** — трудовая функция (ТФ): что специалист способен выполнять.
- **Знания** (что нужно знать) и **умения** (что нужно уметь делать) — пункты
  ТФ, дословно из стандарта. Умение опирается на знания своей ТФ: на странице
  умения показаны знания той же ТФ (сначала — с общими темами), и наоборот.
- **Темы** — поперечный индекс (VPN, ЛВС, криптография, SIEM, ПЭМИН, …, 40
  тем в 7 категориях): одна тема нужна во многих ТФ и должностях.

Темы назначаются правилами — регулярными выражениями из
`src/content/topics.json`, которые `seed.js` применяет к каждому пункту
знаний/умений и к каждому вопросу теста (таблицы `competency_item_topics`,
`quiz_question_topics`; пересобираются при каждом `npm run seed`). Правила
покрывают и формулировки стандартов, и лексику вопросов теста (CVE, SAST,
honeypot, PDCA, …); «ё» и «е» при сравнении не различаются. Покрытие: тему
имеют 96% вопросов теста и 96% пунктов стандартов (без темы — общие пункты
вроде «сущность ИБ»); тест `requirements.test.js` падает, если покрытие
опустится ниже 95% или появится тема, не используемая ни стандартами, ни
тестом. Правила, а не ручная разметка — индекс
воспроизводим, и любое отнесение можно объяснить. Важное следствие для
контента: стандарты почти не называют конкретные технологии — VPN и ЛВС
упоминаются в 4 пунктах каждая, облака и антифрод — ни в одном. Такие темы
есть только в вопросах теста и помечены во вкладке «только в тесте».

По темам в отчёте ревьюера показан результат теста («сети 7/9,
криптография 2/6») — видно, в каких областях пробелы.

## Итоговая оценка (0–100) и AI-резюме

Одно число 0–100 с полным разложением — `src/lib/scoring.js`, считается при
каждом открытии отчёта (и в списке проверок ревьюера).

| Компонент | Макс. | Как считается |
|---|---|---|
| Знания | 45 | Доля верных ответов теста, где каждый вопрос весит `1 + сложность` (сложный — до 2× лёгкого); неотвеченный вопрос считается неверным |
| Темп | 5 | Доля ответов не быстрее 3 с («мгновенное угадывание» — признак ответа без чтения вопроса); при >10% таких ответов — предупреждение |
| Практика | 35 | Средняя оценка ревьюера по заданиям; пока её нет — AI-оценка полноты ответа по рубрике (балл помечается предварительным) |
| Сертификаты | 15 | Только подтверждённые: баллы уровня (entry 3, associate 5, professional/specialty 8, expert 12, вне каталога 3) × (0,25 + 0,75 × доля тем сертификата, нужных этой должности), сумма ограничена 15 |

- **Сложность вопроса** — по уровню квалификации трудовой функции (5 → лёгкий,
  8 → сложный); когда у вопроса накапливаются ответы других кандидатов,
  сложность сдвигается к реальной доле ошибок (байесовское сглаживание, 20
  ответов). Поэтому балл одной и той же проверки может немного меняться по
  мере роста базы — это осознанно: сложность вопросов уточняется данными.
- **Время ответа** — сколько вопрос был на экране при видимой вкладке
  (`test_flow.html`); сервер ограничивает каждое значение 10 минутами, а сумму
  — реально прошедшим с выдачи теста временем. Быстрота сама по себе не
  награждается: оценивается только отсутствие угадывания.
- **Нет данных — не ноль.** Если компонента нет (не оценена практика, старая
  проверка без замеров времени), он исключается и балл пересчитывается на
  оставшийся максимум, с пометкой «предварительно» и причиной.
- **Без сертификатов** максимум 85 — это всё ещё верхний уровень: уровни
  80+ «Эксперт», 65+ «Сильный специалист», 50+ «Уверенный базовый уровень»,
  35+ «Начальный уровень», ниже — «Недостаточно для должности».
- **Самооценка в балл не входит** (её даёт сам кандидат); показывается
  калибровка — завышает, занижает или реалистично оценивает себя.
- **Целостность:** ответы теста отправляются один раз (повторная отправка —
  409, раньше можно было «исправить» ответы после показа результата);
  решение по практике нельзя изменить после оценки ревьюера.

Почему шкала 0–100, а не 250/300: тест из 50 вопросов не различает
кандидатов точнее нескольких баллов из ста — более мелкая шкала изображала бы
точность, которой нет.

**AI-резюме** (`src/lib/aiSummary.js`, кнопка в отчёте ревьюера) — Claude
(`claude-opus-5-5`, структурированный ответ по схеме): профиль кандидата,
сильные и слабые стороны с указанием, на каких данных основан вывод,
полнота каждого практического ответа по пунктам рубрики (что раскрыто, чего
нет), рекомендации для собеседования, настораживающие признаки.
- В модель не уходят ФИО, email, телефон, никнеймы и ссылки на профили.
- Ответы кандидата передаются как данные в тегах; попытка «попросить» модель
  поставить высокую оценку попадает в настораживающие признаки.
- AI не выставляет балл и не принимает решение; его оценка полноты
  участвует в балле только пока нет оценки ревьюера.
- Включён серверный fallback (`fallbacks: "default"`): если классификатор
  безопасности откажет из-за ИБ-тематики ответов (атаки, уязвимости), запрос
  повторяется на рекомендованной модели.
- Каждое формирование — платный запрос к API, поэтому только по кнопке;
  история хранится в `ai_summaries`.

**Ручной режим (без ключа API).** «1. Скопировать запрос» копирует в буфер
тот же обезличенный запрос, что уходит в API, плюс шаблон ответа в JSON;
ревьюер вставляет его в свой чат-ассистент (например, Gemini по подписке) и
вставляет ответ обратно («2. Вставить ответ»). Импорт терпим к тому, как
отвечают чаты — пояснения вокруг, ```json-ограждения, числа строками
(«85%»), отсутствующие необязательные списки, — но проверяет каждое поле той
же схемой и называет поле, если что-то не так. В отчёте резюме помечается
«вставлено вручную: Gemini». Если браузер не даёт доступ к буферу обмена,
запрос показывается в поле для ручного копирования.

## Что не реализовано (сознательно, следующие шаги)

- Выборка 50 вопросов случайная, а не равномерная по компетенциям — в
  отдельной проверке часть ТФ может не попасть в тест; стратифицированная
  выборка сделает баллы разных кандидатов сравнимее.
- Управление ключом шифрования ПДн (ротация, KMS/HSM) — сейчас один ключ из
  переменной окружения; смена ключа требует перешифровки данных.
- Развёртывание Postgres на инфраструктуре в РФ (152-ФЗ ст. 18.5) — сейчас
  локальный dev-инстанс.
- Сброс пароля ревьюера по email — в проекте нет почтовой инфраструктуры.
  Забытый пароль сейчас меняет администратор через `create-reviewer.js`.
- Ограничение частоты входа считается по `req.ip`; за reverse proxy нужно
  включить `app.set("trust proxy", …)`, иначе все запросы будут «с одного IP».
